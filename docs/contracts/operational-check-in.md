# Operational check-in boundary

An authenticated event-scoped admin may `POST /admin/events/:eventId/registrations/:registrationId/check-in` for a confirmed registration. The server records an immutable event attendance fact with actor, session and server timestamp; this does not alter registration or payment state. The endpoint stays for general-entry-only registrations, whose passes grant no activity.

The same authority may `POST /admin/events/:eventId/registrations/:registrationId/activities/:activityId/check-in` with no prior event check-in. Pass entitlements (#124) authorize it: the activity must be in `RegistrationEntitlementsService.accessibleActivityIds`, meaning an active `included` activity of a held pass type or an active selection. Online and in-person registrations therefore behave the same. Only the `workshop` and `competition` kinds are eligible; `battle` was retired in #249 because a battle is the format of a competition. The `0010` trigger still lists `battle`, which is harmless because `activities_kind_ck` rejects it. New labels require an explicit product classification before admission. Archived activities are rejected because the entitlement read is active-only.

One activity check-in runs in one transaction. It records the event attendance fact when it is missing, then the legacy `event_activity_registrations` row when it is missing (the activity fact references it through `activity_check_ins.enrollment_id`; it is no longer the gate), then the activity fact. Each fact keeps actor, session and server time, and a failure rolls back every step. The registration row lock (`FOR UPDATE`) serializes every check-in of one registration, so concurrent first check-ins to two activities share one event fact.

Repeats on both endpoints return `201` with the first fact (its `id` and `checkedInAt`) and `alreadyCheckedIn: true`, without a new row; the stored actor and session stay the first ones. A first check-in returns `alreadyCheckedIn: false`. There is no `409` and no audit table for repeats.

These requests are denied with `400` and no write: a pending, voided or cross-event registration; an activity without pass access, including every activity for a general-entry-only registration; an archived or cross-event activity; and an ineligible kind. Missing or unauthorized admin credentials, origin or CSRF are denied before mutation.

The registration search (`GET /admin/events/:eventId/participants`) returns `registration.generalEntryOnly`, true only when the registration holds at least one pass and every held pass is `general`. Its `activities[]` of `{ id, name, kind, checkedInAt }`, sorted by id, are the accessible `workshop` and `competition` activities from passes (batched through `accessibleActivityIdsByRegistration`), with `checkedInAt` from `activity_check_ins`.

The check-in screen (#336) lists the registrations from the attendee-lists snapshot (`GET /admin/events/:eventId/attendee-lists`, see [Attendee lists](attendee-lists.md)) and derives the same `generalEntryOnly` rule from the held pass classes. It reads the snapshot again after every check-in, so the times shown always come from the server. It offers one action per eligible activity, sorted by name, and the event action only for general-entry-only registrations. A repeat shows the first check-in time. A registration that is not confirmed, has no action, or gets a `400` is sent to main coordination: no registration, pass or competition changes happen at the door. Exceptions require authorized human resolution outside these endpoints; no staff role, override or automatic correction is implied.
