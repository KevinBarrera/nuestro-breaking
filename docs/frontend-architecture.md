# Frontend Architecture

The frontend lives in `apps/frontend` and uses Feature-Sliced Design (FSD). It is a React + TypeScript Vite application with Tailwind CSS, Zustand, and React Router.

## Setup And Commands

Use the repository Node.js version before every project command:

```bash
nvm install
nvm use
pnpm install
```

Run the frontend from the repository root:

```bash
pnpm --filter @nuestro-breaking/frontend dev
pnpm --filter @nuestro-breaking/frontend lint
pnpm --filter @nuestro-breaking/frontend build
pnpm --filter @nuestro-breaking/frontend test
pnpm --filter @nuestro-breaking/frontend test:e2e
```

Pure logic (formatting, parsing, response readers, view models) is unit-tested with Vitest: `test` runs `src/**/*.test.ts` in Node in milliseconds. Colocate each `*.test.ts` next to its module and import it with a same-directory path. `vitest.config.ts` merges `vite.config.ts`, so the `@` alias and plugins match the app; the app's `tsc -b` typechecks the tests and ESLint lints them. Pass time zones explicitly and use fixed dates, so results never depend on the machine's clock or zone. Playwright specs cover user flows: rendering, accessibility, routing, network handling and interaction. When a spec starts enumerating input permutations, move them to a unit test and keep one flow-level assertion in the spec.

Playwright specs in `apps/frontend/e2e` are typechecked: `tsconfig.node.json` includes `e2e` and `playwright.config.ts`, so `build` (`tsc -b`) fails on type errors in specs and ESLint lints them with type information. Specs mock the API with `page.route`; `e2e/support/` holds shared mocks for sweeps across every admin screen.

CI runs the mocked suite inside the official `mcr.microsoft.com/playwright:v<version>-noble` image, which ships the browsers, split into two shards (`test:e2e --shard=<n>/2`) behind the aggregated `frontend / playwright` check. The shards set `NB_E2E_PREVIEW=1`, so Playwright serves a production build (`vite build` + `vite preview`) instead of the on-demand dev server, so specs cannot load `/src/...` modules in the browser; test pure modules with Vitest instead. On pull requests the shards also set `NB_E2E_SKIP_SWEEPS=1`, which skips the theme × screen sweeps (`admin-accessibility.spec.ts`, `admin-phone-width.spec.ts`, `public-phone-width.spec.ts`); every push to `dev` runs them, and feature specs keep their own phone-width checks on PRs. Run them locally with plain `test:e2e`. The one dev-server-only assertion (session store cleared on sign-out) runs again without preview in shard 1. The live check-in job stays on the host runner because its backend starts PostgreSQL with Testcontainers, which needs the host Docker daemon. The image tag in `.github/workflows/pr-checks.yml` must match the exact `@playwright/test` version in `pnpm-lock.yaml`; bump both together.

On pull requests, a `quality / changes` job decides which areas run: backend jobs run only when `apps/backend/**` changes, frontend lint, unit tests, build and Playwright only when `apps/frontend/**` changes, and the live check-in job when either changes. Docs-only files (`docs/**`, `odd/**`, `openspec/**`, `*.md`) run no area. Any other file outside the two apps (lockfile, workspace or tool config, workflows, scripts) and every push to `dev` run everything; `quality / format` always runs. If change detection fails, every area runs instead of being skipped. Skipped shards still let `frontend / playwright` pass, so the check name stays stable.

## FSD Layers

- `app/` contains application bootstrap, global styles, providers, and router wiring.
- `pages/` contains route-level screens. The current slices are `public-purchase`, `account-activation`, `admin`, `dancer`, and `not-found`. The team screens (`admin-team-page.tsx`, `team-list.tsx`, `admin-team-new-page.tsx`, `invitation-created.tsx`, `team-dialogs.tsx`, with the pure `team-model.ts` and `team-form-model.ts`) live in `pages/admin`. So do the event lifecycle screens of #213: the event list (`admin-page.tsx`, with the pure `event-model.ts`) and Nuevo evento (`admin-event-new-page.tsx`, with the pure `event-form-model.ts`).
- `widgets/` contains reusable page-level compositions. `widgets/admin-shell` is the admin frame (see [Admin Shell](#admin-shell)). `widgets/public-layout` is the public purchase frame: brand bar, navy header with an optional 44px "Volver" link and the theme toggle, "Paso N de 4" progress, the sticky bottom bar of pases (pass count, total, "Continuar"), and `StepBar`, the sticky bottom bar of the later steps ("Atrás" and the step's primary action).
- `features/` contains user-facing actions. `features/theme-toggle` is the light/dark switch. `features/public-purchase` is the pure model of the public purchase (#176): pass selection rules by `passClass` and `requiresPassClass` (a full pass removes and blocks general entry; an add-on needs its required class and is dropped when it goes), per-pass hints, competitions per chosen pass and whether that step applies, totals, buyer validation mirroring the backend limits with Spanish messages (phone is 10 national digits sent with a `+52` prefix) plus the first invalid field and whether an error sits in the optional details block, the registration request, server `fieldErrors` and failure messages, and the versioned `sessionStorage` draft format per slug. For Revisa y paga it builds the summary rows (`reviewLines`, `reviewBuyer`, `displayPhone`), maps a failed payment to its message and fixing screen (`payFailure`), maps a failed checkout start to its message and whether to retry (`checkoutFailure`), accepts only an absolute `https:` checkout URL (`safeCheckoutUrl`), and reads the registration id on the Mercado Pago return URL (`paymentReturnRegistration`, which never reads Mercado Pago's own params). It also groups pass options by class for the screens (`passGroups`). The screens in `pages/public-purchase` own storage access and money formatting (`formatMxn` from `@/entities/event-catalog`).
- `entities/` contains business models. `entities/session` defines the typed user role and session model; `judge` is an admin-capable role. `entities/public-event` reads the public catalog, creates a pending registration ([public catalog](contracts/public-event-catalog.md), [public registration](contracts/public-registration.md)) and starts its Mercado Pago checkout (`createCheckout`, `POST /public/events/:slug/registrations/:registrationId/checkout`, #177) without credentials or CSRF (`credentials: 'omit'`). Responses pass runtime guards, and failures throw `PublicEventError` with a discriminated `failure`: `not-found`, `sales-closed` (reason), `invalid` (`fieldErrors`), `rule` (409 code), `unavailable`, `not-payable` (409 `registration_not_payable`), `provider-unavailable` (502 `payment_provider_unavailable`), `rate-limited` or `error`. Successful create, edit, archive, restore and delete writes notify `onAdminEventsChanged` listeners, so the shell's event selector reads the list again.
- `entities/admin-team` is the team management API (#214, [admin auth boundary](contracts/admin-auth-boundary.md)): list, invite, new link, cancel, change access, deactivate and reactivate, with runtime readers. Writes fetch the CSRF token from `GET /auth/session` first. Failures throw `TeamError` with a typed `failure`: `denied` (401 or 403, including the CSRF prefetch), `invalid` (400 `fieldErrors`), `rule` (a known 404 or 409 `code`), `unknown` (the request was sent but its answer was lost or unreadable, so a write may have been applied) or `error`. The public activation calls (`checkActivation`, `activateAccount`) live in `entities/session` and send no cookies.
- `entities/admin-event` is the event lifecycle API (#213, [admin event lifecycle contract](contracts/admin-event-lifecycle.md)): `getEventFoundation` (`GET /admin/events/:eventId/foundation`: the event, its venues and its `deleteBlockers`, read as `null` when missing or holding an unknown kind), `listAdminEvents` (`GET /admin/events`, with `{ archived: true }` for `?archived=true`; each row is the full `AdminEvent`, dates and sales switch included), `createEvent`, `updateEvent`, `archiveEvent`, `restoreEvent`, `deleteEvent` (with the typed slug) and the venue writes `createVenue` and `renameVenue`, with runtime readers (a list with any malformed row or non-UUID id is rejected as a whole). Writes fetch the CSRF token from `GET /auth/session` first. Failures throw `AdminEventError` with a typed `failure`: `unauthorized` (401, including the CSRF prefetch), `forbidden` (403), `invalid` (400 `fieldErrors`), `rule` (409 `slug_taken`, `organization_ambiguous`, `event_archived`, `event_not_archived` or `venue_shared`), `not_empty` (409 `event_not_empty` with its known `blockers`), `not_found` (404), `unknown` (the request was sent but its answer was lost or unreadable) or `error`.
- `entities/flagged-payments` reads the event's Mercado Pago payments flagged for manual review (#230, [flagged payments contract](contracts/flagged-payments.md)): `getFlaggedPayments` (`GET /admin/events/:eventId/flagged-payments`) with a runtime reader that rejects unknown reasons. Failures throw `FlaggedPaymentsError` with a typed `failure`: `denied` (401 or 403), `not-found` (404) or `error`.
- `entities/admin-registration` is the in-person sale API (#105, [admin registration operations](contracts/admin-registration-operations.md), [event catalog](contracts/event-catalog.md)): `searchRegistrations` (`GET /admin/events/:eventId/participants`; a query outside 2 to 200 characters is rejected before any request), `createManualRegistration` (only the participant fields, never `activityIds`, plus `confirmedDuplicateRegistrationIds` when the operator confirms possible duplicates), `addRegistrationPass`, `setPassSelections` (with an optional `reason`, sent only when given; #170), `getRegistrationEntitlements` (the held passes plus a registration summary: id, status, folio, participant name and AKA, and `cash`, the current cash payment `{ amountCents, receipt }` or null; a missing or malformed `cash` rejects the answer) and `confirmCashPayment` (`amountCents` is sent as `amount`), with runtime readers. Writes fetch the CSRF token from `GET /auth/session` first. Failures throw `AdminRegistrationError` with a typed `failure`: `unauthorized` (401, including the CSRF prefetch), `forbidden` (403), `invalid` (400 `fieldErrors`; the cash amount and receipt messages map to `amountCents` and `receipt`), `rule` (a known `code` such as `receipt_taken`, or a known backend message such as `pass_already_held` or `add_on_requires_full`; an unknown message is `error`), `possible_duplicates` (409 with every masked match readable, so a duplicate is never confirmed unseen), `not_found` (404), `unknown` (a write whose answer was lost or unreadable, so it may have been applied) or `error`.
- `entities/registration-history` reads an event's registration history (#104, [admin registration operations](contracts/admin-registration-operations.md#registration-history-104)): `getRegistrationHistory(eventId, { filter, cursor?, q? }, signal)` (`GET /admin/events/:eventId/registration-history`) always sends `filter` (`all`, `corrections`, `on_site` or `complimentary`, #356), `q` only when searching and `cursor` only after the first page, leaving the page size to the backend default (50). Its reader `readHistoryPage` requires `counts`, copies only the whitelisted fields, reads an unknown `details.kind` as `other` and rejects the whole page when a known kind has a malformed field. Failures throw `RegistrationHistoryError` with a typed `failure`: `denied` (401 or 403), `not-found` (404) or `error`.
- `entities/attendee-list` reads the printable attendee lists (#65, [attendee lists contract](contracts/attendee-lists.md)): `fetchAttendeeLists` (`GET /admin/events/:eventId/attendee-lists`) with a reader that rebuilds each row field by field, so a contact field sent by mistake never reaches the screen, and reads a pass type's `status` as `archived`. Failures throw `AttendeeListsError` with a typed `failure`: `denied` (401 or 403), `not-found` (404) or `error`.
- `entities/participant` is the shared #58 participant form model, used by the public Tus datos form (`features/public-purchase` wraps it in the buyer's voice) and the admin in-person sale (#105, `pages/admin/ui/sale-participant-model.ts`, in the operator's voice): the fields, empty form, backend length limits, labels, the optional details block, the calendar-date and Instagram handle rules, `validateParticipant` (each form passes its Spanish messages and its phone rule), `participantPayload` (each form passes how the phone is sent), `firstInvalidField` and `localIsoDate`. The in-person sale takes a Mexican phone (10 digits, sent as `+52 <digits>`) or an international one (optional leading `+`, 10 to 15 digits, sent as `+<digits>`).
- `shared/` contains framework-agnostic configuration, general utilities, and reusable UI primitives. `shared/lib` also holds `formatLinkExpiry` (a link's expiry in Spanish, local time) and `hasControlCharacters` (the control-character rule the backend applies to passwords and reasons).

Dependencies point downward: `app -> pages -> widgets -> features -> entities -> shared`. A layer can only import from layers to its right. Code outside a slice must use that slice's `index.ts` public API. Internal imports may use `./`; parent-directory imports are prohibited workspace-wide.

## Import Enforcement

`apps/frontend/eslint.config.js` uses ESLint's `no-restricted-imports` rule to enforce layer direction and block deep alias imports. For example, use `@/entities/session` rather than `@/entities/session/model/types`, and use `@/features/check-in` rather than internal feature paths when a future feature slice is added.

The rule applies to future `features` and `widgets` directories as well. A slice imports its own internal files with `./`, which keeps its public API explicit and prevents cross-feature deep imports.

## Route Areas

- The public purchase (#176) needs no login and sits outside every session boundary. `/` shows the event whose slug is in `VITE_PUBLIC_EVENT_SLUG` (unset or blank shows "No hay evento a la venta"); `/e/:slug` shows any event. The steps always live under the event address: `/e/:slug/pases`, `/e/:slug/competencias`, `/e/:slug/datos` and `/e/:slug/revisar`, plus `/e/:slug/pago`, where Mercado Pago sends the buyer back (#177), so the browser back button walks the steps and "Comprar pases" on `/` goes to `/e/<configured slug>/pases`. One pathless layout route (`PublicPurchaseLayout`) wraps them all, so the catalog loads once per slug (loading, "Este evento no existe", and error or rate-limit notices with "Reintentar"). It holds the selection and buyer draft and saves them to `sessionStorage` per slug; a restored draft goes through `normalizeSelection` against the fresh catalog.
  - Inicio (`/` and `/e/:slug`): event name, dates on the event clock, "Comprar pases" while sales are open, the passes with catalog prices grouped by class, the Mercado Pago note and a footer with the three legal document pages. Closed sales show "La venta abre el <fecha>" when the opening is ahead, otherwise "La venta en línea está cerrada", and no buy button or passes.
  - Pases (`/e/:slug/pases`): checkbox cards grouped as "Pases completos", "Adicional" and "Solo asistir", with the rule hints and disabled states from `passOptions`. "Continuar" stays disabled with a hint until a pass is chosen, then goes to competencias when a chosen pass has competitions to pick, else to datos. Phones get the sticky bottom bar; from `lg` up the same state shows in a "Tu compra" side panel.
  - Competencias (`/e/:slug/competencias`, optional): one `fieldset` per chosen pass with competitions to pick, each competition a toggle button (`aria-pressed`, check mark when on) that wraps at 375px; competitions a pass includes show an "Incluida" badge. The bottom bar (`StepBar`) has "Atrás" (pases) and "Continuar" (datos).
  - Tus datos (`/e/:slug/datos`): the buyer fields of the [public registration](contracts/public-registration.md), with both last names side by side, the email hint, a fixed `+52` before the phone, and city, Instagram, level and birth date inside a collapsed "Más datos (opcional)" block. Values go to the draft as typed. "Revisar compra" validates with `validateBuyer`: errors show under each field and in a summary at the top (`alert`), the first invalid field gets focus, and the details block opens when an error is inside it; after that first attempt errors update while typing. Valid data goes to revisar. "Atrás" goes to competencias, or to pases when that step is skipped.
  - Revisa y paga (`/e/:slug/revisar`): a "Tus pases" card (each chosen pass with its picked and included competitions and its price, the total in MXN, "Cambiar" to pases), a "Tus datos" card (full name · AKA, email · `+52` phone, "Cambiar" to datos), the overlap notice (`role="note"`), and the "Documentos y políticas" fieldset with three required `CheckboxField`s, each linking its legal document page in another tab ("(se abre en otra pestaña)" for screen readers). The request sends the version of each document as `legalAcceptances` (#180); a 400 on those fields (a version changed since the page loaded) asks the buyer to reload and accept again. "Pagar $X con Mercado Pago" in the `StepBar` stays disabled, described by "Marca las tres casillas para poder pagar.", until all three are checked. Paying calls `createRegistration` (D1) and then `createCheckout` for the new pending registration (#177): the button turns into a disabled "Te estamos llevando a Mercado Pago…" and a synchronous guard blocks a second request. When the checkout URL passes `safeCheckoutUrl` (anything but `https:` counts as a failure), the draft is removed from `sessionStorage` and `window.location.assign` sends the browser to Mercado Pago's hosted page with a full page load; a page restored from the back/forward cache leaves the pending state. A failed checkout keeps the registration id in the page: a danger `Notice` from `checkoutFailure` says nothing was charged and offers "Reintentar", which (like "Pagar") asks only for a new checkout, never a second registration. 502 `payment_provider_unavailable`, network errors and 429 can be retried; `registration_not_payable` cannot (the id is dropped, so "Pagar" starts over); closed sales and 404 link to the home. After a reload the id is gone, but the draft is still there and the backend reuses the buyer's pending registration. Registration failures keep the draft and show a danger `Notice` from `payFailure` above the button, with a link to the screen that fixes them: server `fieldErrors` on buyer fields are listed with their labels and "Corregir mis datos" (the data already passed the same validation on datos, so a list with a link is clearer than sending the buyer back unasked); pass errors and rules link to pases or competencias; closed sales and an unknown event link to the home with a full page load, so the catalog is read again; 429 says "Demasiados intentos, espera un momento e intenta de nuevo."; `registration_unavailable` and network or server errors show their message and the button stays available to retry.
  - Pago (`/e/:slug/pago?registration=<id>`, `PublicPaymentReturnPage`): Mercado Pago's return for every outcome. A minimal screen until #178 adds the result states (polling, confirmed with folio, pending OXXO or SPEI, rejected with retry): the heading "Estamos confirmando tu pago" and a `role="status"` message that the confirmation and folio arrive by email once Mercado Pago notifies us, plus "Volver al inicio". It never reads `status=approved` or any other Mercado Pago param; only the verified webhook confirms a payment. It sits outside the purchase layout (no catalog load). The temporary reserved screen (`/e/:slug/reservada`) was removed in #177 without a redirect: it never left `dev`, so no buyer bookmark points to it, and the path now shows the not-found page.
  - Documentos legales (`/legal/reglamento`, `/legal/privacidad`, `/legal/cancelacion`, `pages/legal-document`, #180): static pages outside the purchase layout (no catalog, no API call) with the title, "Versión: <version>", a "Texto provisional" notice and "Ir al inicio". Titles, paths and versions live in `shared/config/legal-documents.ts`; the backend checks the same versions, so a new text changes the version in both apps. The texts are placeholders until the organizer delivers them (#182). `e2e/public-legal-documents.spec.ts` covers the three pages and the home footer link; the public phone-width sweep includes the reglamento page.
  - Guards (`stepRedirect`): every step after pases sends the buyer to pases when no pass is chosen (a bookmark, or a draft emptied by a catalog change), competencias goes to datos when no chosen pass has competitions to pick (D6), and revisar goes to datos when the saved buyer data does not pass `validateBuyer`. Every redirect replaces the history entry.
  - Checks: `e2e/public-purchase-review.spec.ts` covers home → the Mercado Pago checkout (a fake `https://example.test` page) with the exact POST body (no cookie or CSRF header on either request), every registration failure kind, a 502 checkout with "Reintentar" that calls only the checkout again, the removed reserved path and a 1280px review layout; `e2e/public-payment-return.spec.ts` shows the return page makes no confirmation claim even with `?status=approved`; `e2e/public-phone-width.spec.ts` sweeps every public screen at 375px in both themes (no horizontal scroll, 44px targets; inline document links inside a checkbox label count through their 44px row). Public screens stay out of the admin sweep lists.
- The admin and dancer areas are lazy routes (`lazy` in `app/router`), so the public entry bundle does not include them. When a chunk fails to load (typically a tab opened before a deploy), their `errorElement` shows "No pudimos cargar esta página" with a "Recargar" button.
- `/admin` is the administration route area. Admins and judges belong here in the initial scope.
  - `/admin` itself is the event list ("Eventos"), built only from `GET /admin/events` (client in `entities/admin-event`): each active event is one card-sized link to its overview (#323): a decorative date tile (`eventDateTile`: "Nov 2026" over "21–22", or a dashed "Por definir"), named by the event and described by its dates on the event's clock ("14–15 de noviembre de 2026", or "Fechas por definir"), its location (`eventLocation`: city and state, plus the country outside Mexico; nothing while the event has none, never the time zone; #322), its public address (`/e/<slug>`) and a sales pill with a dot, with loading, error (with "Reintentar"), access-denied and empty states. The chip ("Venta abierta" on `bg-success`, "Venta cerrada" on `bg-chip`) follows only the list's `salesEnabled` switch: the list does not carry the sales window, so an event with sales on outside its window still reads "Venta abierta"; the overview's "Venta en línea" shows the exact state. When a reload fails after the list was shown (for example right after a restore), the last list stays and a non-blocking `role="status"` notice says it may be stale, with "Reintentar". Global admins (#213) also get "Crear evento" (to `/admin/events/new`) and ask for `?archived=true`: the list is split in "Activos" and "Archivados" tabs with counts (`role="tablist"`, arrow keys move between them); archived cards show an "Archivado" badge and "Restaurar", and an empty Archivados tab says "No hay eventos archivados". Restoring posts the restore, reads the list again, goes back to Activos, focuses the "Eventos" heading and says that sales stay closed. Datos del evento comes back here after archiving or deleting an event, with a `{ notice }` in the navigation state that the list shows once (it is then cleared from the history entry). With no active event a global admin sees the first-run state ("Aún no hay eventos", three numbered step cards and "Crear evento"; "No hay eventos activos" when some are archived, inside the tabs); an event-scoped admin sees "No hay eventos disponibles para tu cuenta." without the button. Only accounts that cannot create events are redirected (replace navigation) to the overview when exactly one active event exists, so a global admin is never trapped away from "Crear evento" or Archivados. The redirect applies when `/admin` is opened directly (a bookmark, sign-in); the shell's links to the list ("Todos los eventos" and the brand) carry `eventListRequest` history state, so an event-scoped admin with one event who asks for the list sees it instead of being sent straight back. An archived event's screens still open from a direct link; the shell's event selector, whose list leaves archived events out, stays hidden there, and it reads the list again (`listAdminEvents`, so it uses the same reader) once when the URL names an event it does not have yet (a new one), and after every event write that changes the list. It shows no sample or planning data.
  - Nuevo evento (`/admin/events/new`, global admins only; everyone else sees "Sin acceso"; the side navigation does not read `new` as an event id) has the breadcrumb "Eventos / Nuevo evento" and one form card (#323): "Datos generales", then an "Identificadores permanentes" panel, the closed-sales note and "Cancelar" / "Crear evento". Fields, in screen order: "Nombre del evento"; "Ubicación" (`location-fields.tsx`: "Ciudad", "Estado" and "País", a `Select` of countries with México first and by default; all three required, #322); "Zona horaria", a shared `Select` with a short list of Mexican IANA zones (default `America/Mexico_City`); optional "Inicio" and "Fin" `datetime-local` fields on that zone's clock, sent as instants with `fromZonedInput`; then, in the panel, "Dirección de la página de compra" with the fixed `/e/` prefix, suggested from the name by `slugify` (lowercase, no accents, other characters become single hyphens, at most 80) until it is edited by hand; and "Prefijo de folio", uppercased as typed, next to "Así se verá un folio" (`<PREFIX>-7K3Q`, or `PREFIJO-7K3Q` until there is a prefix). `validateEvent` mirrors the backend rules (name, location, slug, prefix, both dates or neither, end after start, no skipped DST time) and focuses the first invalid field; server `fieldErrors` map to the same fields, `slug_taken` shows "Esta dirección ya la usa otro evento. Elige otra." under the address (the API does not name the other event), `organization_ambiguous` and other failures show a page alert, and a lost answer (or a later `slug_taken` for the same address) says the event may exist and links to Eventos. Success opens the new event's overview, where the catalog and sales start. The form uses `UnsavedChangesGuard`.
  - Datos del evento (`/admin/events/:eventId/foundation`, the former read-only "Fundamentos del evento"; #213 D2, D8; side navigation "Configuración › Datos del evento", header label "Datos del evento") reads `GET /admin/events/:eventId/foundation` through `getEventFoundation` (event and venues; activities are left out, the Actividades screen shows them). The page is laid out in sections (#323, `settings-section.tsx`: title and description on the left, a card on the right, stacked when narrow): General, Identificadores, Sedes and, for global admins, Archivar o eliminar. The General form edits "Nombre del evento", the same "Ubicación" fields (an event created before #322 shows them empty with México, saves other edits without a location, and needs all three once a city, a state or another country is chosen; a stored location can change but not be cleared), "Zona horaria" (the Nuevo evento `Select` list, with the stored zone added first when the list lacks it) and the optional "Inicio" and "Fin" `datetime-local` fields, shown on the event's clock with `toZonedInput`. Dates are wall-clock times on the selected zone, as in Nuevo evento, so changing the zone keeps the typed times and moves the instants (both dates are sent). Pure logic is in `event-details-model.ts` (dirty detection against the loaded values, the changed-field `PATCH` body, venue name rule); validation shares `validateEventDetails` with Nuevo evento. While the form differs from the loaded values, a sticky "Cambios sin guardar" bar at the bottom says "Tienes cambios sin guardar" with "Descartar" and "Guardar cambios" (a submit for the General form); it is not shown otherwise, nor to judges or on an archived event; a save sends only the changed fields (a name that only gained surrounding spaces sends nothing), maps server `fieldErrors` to their fields, says "Cambios guardados." and restarts the form from the answer. Identificadores shows `/e/<slug>` with "Copiar" ("Copiada", announced; a failure says to copy it by hand, the same `useCopyText` as the Resumen sales card) and the folio prefix with an example folio, read-only. The form uses `UnsavedChangesGuard`. Global and event-scoped admins edit; judges (who may read the foundation) get the same screen read-only with a "Solo lectura" notice and no actions. An archived event, or one whose save or venue write gets `event_archived`, shows an "archivado" notice and the screen turns read-only (an open venue form closes); the notice tells global admins to restore it below and everyone else to ask a global admin. Answers are applied to the latest state through `event-details-state.ts` and dropped when they belong to an event that is no longer shown, so a venue added while a save is pending stays and switching events mid-save opens the new event. ## Workspace Reuse

Keep code in `apps/frontend` until there is demonstrated reuse. Create a workspace package only when a UI primitive or API layer has a real shared consumer or requires an independent lifecycle. Do not extract packages preemptively.

## Design System

The [Los más pesados design system](https://claude.ai/artifact/7SRpK5YDMUVAEzuC5RNDef) (#257, approved by the product owner on 2026-10-16) is the visual reference for every admin and public screen. It shows each `--nb-*` token in both themes, the type scale, spacing and radius, the `shared/ui` components with live previews and usage guidelines, and the brand assets (logos, characters, scenes and flyers).

- **New UI follows it.** New screens and components use its tokens and `shared/ui` components. When something they need is missing from it, add it to the code first (token or shared component), then to the design system, instead of styling one page by hand.
- **Touched UI moves toward it.** When a change touches an existing screen or component that does not follow the design system, bring that screen or component in line in the same PR, in a separate commit (`style(...)` or `refactor(ui)`), so reviewers can tell the polish from the behavior change. Do not polish screens the PR does not otherwise touch; open an issue for drift found elsewhere. A large change to a shared component in `shared/ui` gets its own PR.
- **Code is the source of truth.** The design system was built from `src/app/styles/index.css` and `src/shared/ui`. When a token or component changes in code, update the design system to match.

## Theme System

The admin UI has a light and a dark theme built on CSS custom properties in `src/app/styles/index.css`.

- **Tokens.** Each theme defines semantic `--nb-*` properties (`--nb-surface`, `--nb-fg`, `--nb-muted`, `--nb-line`, `--nb-success-bg`, ...) under `:root[data-theme='light']` and `:root[data-theme='dark']`. Pages inside the admin shell never reference the raw event palette (`--event-*`) directly; the sign-in screen in `AdminSessionBoundary` keeps its own fixed dark palette.
- **Utilities.** `@theme inline` maps tokens to Tailwind colors, so `bg-surface`, `text-muted`, `border-line`, `bg-primary text-primary-fg`, `bg-success text-success-fg`, `bg-chip` and friends follow the active theme. `bg-page` and `bg-brand-bar` are custom utilities for the gradients.
- **Rule.** Admin UI uses only these theme utilities, never raw hex values or default Tailwind palette colors, so both themes stay correct. Text pairs must keep 4.5:1 contrast, control borders (`--nb-input-line`, `--nb-eligible-line`) 3:1 against every ground they sit on, and controls a 44px minimum height; `e2e/admin-accessibility.spec.ts` checks all three and `e2e/admin-phone-width.spec.ts` checks every admin screen at 375px in both themes.
- **Selected chips.** Filter chips are transparent with a border when unselected; the selected chip uses `bg-chip-selected text-chip-selected-fg` (`--nb-chip-selected-*`: indigo on cream text in light, cream with indigo text in dark), so it differs in lightness, not only hue, and shows the shared `CheckIcon` from `@/shared/ui`. `e2e/admin-accessibility.spec.ts` checks both chip states for 4.5:1 text and at least 3:1 between their backgrounds in both themes.
- **Preference.** `@/shared/lib` (`theme.ts`) reads and writes the `nb-theme` key in `localStorage` with guards: any storage failure falls back to light without throwing. `@/features/theme-toggle` renders an icon-only 44×44 button whose name states the action: a moon named "Cambiar a tema oscuro" in the light theme and a sun named "Cambiar a tema claro" in the dark theme (no `aria-pressed`; a matching `title` shows on hover).
- **No flash.** An inline script in `index.html` sets `data-theme` on `<html>` before first paint; keep its key in sync with `theme.ts`.
- **Fonts.** Archivo (UI) and IBM Plex Mono (prices, times, folios: `font-mono`) load from Google Fonts through a non-blocking `rel="preload"` that swaps to a stylesheet on load, with a `<noscript>` fallback. `--font-sans` and `--font-mono` end in system fonts, so the UI stays usable when the font host fails. Playwright blocks the font hosts by DNS so specs stay offline.
- **App icons.** The event's graffiti logo is the favicon (`favicon-16x16.png`, `favicon-32x32.png`, and `favicon.ico` for older browsers), the iOS home-screen icon (`apple-touch-icon.png`) and the `site.webmanifest` icons (192 and 512px), all in `public/` and linked from `index.html`. These files come from the design system (#257); replace them as one set. `e2e/app-icons.spec.ts` checks the links and that every file is served.

## Shared Select

`@/shared/ui` exports `Select`, built on React Aria Components (`react-aria-components`, the only third-party UI dependency). Admin screens use it instead of native `<select>` elements so the trigger and the open listbox follow the theme tokens.

- **API.** `label`, `options` (`{ id, label, isDisabled? }`), `selectedKey`, `onSelectionChange(key)`, optional `name`, `isDisabled`, `placeholder`, `hideLabel` (screen-reader-only label), `variant` (`field` for forms, `header` for the topbar, `nav` for the side navigation, where the list keeps the trigger's width and long names wrap, `chip` for table cells) and `triggerClassName` (for example a chip tone). Keys are non-empty strings; map an empty value such as "Ninguno" to an explicit key. Re-choosing the current option does not call `onSelectionChange`.
- **Accessibility.** The trigger is a `button` with `aria-haspopup="listbox"` whose name is the selected value followed by the label (for example "Encuentro del barrio Evento"). Enter, Space or the arrow keys open the listbox with focus on the selected option, which is marked `aria-selected` and shows a check icon. Options are at least 44px tall.
- **Hidden native select.** React Aria renders an `aria-hidden`, untabbable native `<select>` beside the trigger for autofill and `FormData`; specs ignore it (`e2e/support/select.ts`) and must not interact with it.
- **Specs.** Use `selectTrigger`, `chooseOption` and `expectSelected` from `e2e/support/select.ts`; the listbox renders in a popover at the end of `<body>`, outside the trigger's form or region.

## Shared Dialogs

`@/shared/ui` also exports dialog primitives built on React Aria's `ModalOverlay`, `Modal` and `Dialog`. Focus stays inside the open dialog, Esc closes it, and focus returns to the control that opened it. Dialogs fit a 375px screen, and a tall body scrolls while the title and buttons stay visible.

- **`Modal`.** The base dialog. It needs a `title` (the accessible name) and takes an optional `description`, body `children` and `actions` (or a function that receives `close`). Use it inside `DialogTrigger` (also exported) or control it with `isOpen`/`onOpenChange`. Clicking the backdrop does not close it unless `isDismissable` is set.
- **`ConfirmDialog`.** A controlled `alertdialog` for actions with consequences, such as archiving: `title`, `consequence`, `confirmLabel`, `cancelLabel` ("Cancelar" by default), `tone="destructive"` for a filled danger button, and `isPending` (with an optional `pendingLabel`), which disables both buttons and Esc while the action runs. The caller closes it once the action succeeds. When the action removes the control that opened it (an archived activity loses its "Archivar" button), the caller moves focus to a stable target: after an archive the activities page focuses its heading, under which the success notice is announced, and after a restore (default tone, "Restaurar" on an archived row) it focuses the restored row's "Editar", or the heading when that row is not shown. The pass list does the same after a pass restore, focusing the restored card's link.
- **`ReviewChangesDialog`.** A controlled "Revisar cambios" dialog for edit forms. It lists each changed field as label and before → after, with "Guardar cambios" and "Volver a editar" (which closes it and keeps the form's edits), plus `isPending`. Build its `rows` with `changedRows(fields)`, and use `hasChanges(fields)` to skip the review when nothing changed. Both compare displayed values, so pass a `format` (for example for prices) when two stored values display the same. Text is not trimmed.
- **`UnsavedChangesGuard`.** Render `<UnsavedChangesGuard when={dirty && !saving} />` on a screen with unsaved edits. While `when` is true, in-app navigation to another path (links, breadcrumbs, the side navigation, back and forward) is held with the data router's `useBlocker` and confirmed in a destructive `ConfirmDialog` ("¿Salir sin guardar?", "Salir sin guardar" / "Seguir editando"), and a reload or tab close gets the browser's own prompt through `beforeunload`. Turn it off while a save is in flight, so the navigation that follows a successful save (create → detail, archive → list) is never blocked; once the confirmed save is applied the screen is clean again.
- **`buttonClass(tone)`.** Shared button classes (`primary`, `secondary`, `danger`, `destructive`) with 44px targets, for shared UI that cannot import page styles.

## Shared Form Fields

`@/shared/ui` exports form primitives for public forms, styled with theme utilities only (`bg-input`, `border-input-line`, `text-danger-fg`, focus outline) and 44px targets:

- **`TextField`.** `label`, optional `hint`, `optional` (adds "(opcional)"), `error`, and a fixed `prefix` such as `+52`; other input props pass through. The input itself is the 44px target, inside the bordered frame. The prefix, hint and error are linked with `aria-describedby`, and an error sets `aria-invalid`. `hintPlacement="below"` moves the hint under the input (default `above`, under the label).
- **`CheckboxField`.** A native checkbox inside its label (the label may hold links), with optional `description` and `error`, linked the same way.
- **`FieldError` and `Notice`.** Inline error text, and a block message (`tone="danger"` is an `alert`, `info` a `status`).

## Shared Data Table

`DataTable` (`@/shared/ui`, #317) is the titled table card of the UI canvas ("Componente · Tabla"): a title and optional description, sentence-case column headers on a tinted band, rows at least 52px tall, and an optional tinted footer with a count on the left and a note on the right. Columns are `{ key, header, cell(row), rowHeader?, align?, muted?, mono? }`: `rowHeader` renders the naming column as `<th scope="row">`, `align: 'end'` and `mono` are for amounts. With no rows it shows the `empty` text instead of the table. Below `minWidth` (default `45rem`) the table scrolls inside the card, so the page never scrolls sideways. Links inside cells keep a 44px target (`inline-flex min-h-11`). `TableChip` is the neutral chip for a short category in a cell, such as a pass class.

## Shared Breadcrumbs

`Breadcrumbs` from `@/shared/ui` marks where a nested screen sits (for example "Pases › Pase completo"). Its `items` of `{ label, to? }` render a `nav` named "Ruta de navegación" with an ordered list: earlier items are links with 44px targets, and the last item carries `aria-current="page"`. The "›" separator is generated by CSS, so it stays out of the item names, and long labels wrap at 375px. `variant="link"` (Agregar administrador) shows pink underlined links, a "/" separator and a muted current page; the default stays as described.

## Admin Shell

`@/widgets/admin-shell` (`AdminShell`) wraps every protected `/admin` page through `AdminSessionBoundary`. It renders the header (brand, theme toggle, sign-out), the brand bar, and the full-height side navigation. The brand "LOS MÁS PESADOS" is a link to the event list (`/admin`, named "Los más pesados, ir a todos los eventos"). The side navigation (#313, 288px wide from `md` up) has two sections. "General" holds "Todos los eventos", shown to every admin and current on the event list and Nuevo evento, and "Equipo" for global admins. "Evento" holds three collapsible groups, each a button with `aria-expanded`: Operación (Resumen, Check-in, "Pagos por revisar", #230, "Inscripciones", #105, "Historial", #104, and "Listas de respaldo", #65), Catálogo (Actividades, Pases) and Configuración ("Datos del evento", #213). The group of the current section opens on its own and groups the admin opened stay open (`side-nav-model.ts`); a closed group renders no links. Above the groups sits the event selector (`EventSelector`, a `nav` variant `Select` fed by `GET /admin/events`): inside an event it shows its name and switching keeps the current section; without one it reads "Elige un evento" and a choice opens that event's Resumen. It stays hidden until the list loads and inside an event the list lacks (an archived one). Without an event in the URL the groups are disabled with a lock icon, so the list has a single current item. "Pagos por revisar" shows a count badge when the event has flagged payments (`useFlaggedPaymentsCount`, read once per event; a failure shows no badge). Every section has a screen, so the nav has no "Próximamente" items. Pages render only their own `<main>`. Signing out replaces the URL with `/admin`, so signing back in starts from the event entry instead of the previous screen. While the shell (or any `bg-page` frame) is shown, `html` paints the themed `--nb-page` background and `html`/`body` set `overscroll-behavior: none`, so overscroll never reveals a different color.

- **Fixed frame.** From `md` up the shell is one viewport tall (`h-dvh`): the header, brand bar and side navigation stay in place, and only the content column around the page's `<main>` scrolls (`overflow-y-auto`); the side navigation scrolls on its own if it outgrows the height. The shell scrolls that column back to the top on every route change, because the window no longer scrolls. Popovers such as the shared `Select` listbox render at the end of `<body>`, so the scroll container never clips them.
- **Phone.** Below `md` the navigation stacks above the page content and the whole page scrolls naturally with no horizontal overflow. `e2e/admin-fixed-shell.spec.ts` covers both layouts.
- **Print.** `print:` variants hide the header, brand bar and side navigation and put the frame back in normal flow (no fixed height or inner scroll), so a printout holds only the page's `<main>`. The `@media print` block in `app/styles/index.css` maps the `--nb-*` tokens to black on white in both themes and sets `@page { margin: 12mm }`. Listas de respaldo uses `print:break-before-page` per list, `print:break-inside-avoid` per row and a repeated `<thead>` for the per-page heading.
