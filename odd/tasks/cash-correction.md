# Correct a confirmed cash payment's amount or receipt number

## Tracking

- GitHub issues: #104 (fourth slice: cash correction) and #256 (its UI action)
- Branch: `feat/104-cash-correction` → `dev` (base `cff009e`), one commit per task. Split into chained PRs if the diff passes ~400 lines.

## Goal

An administrator corrects the amount or the receipt number of a confirmed cash payment after checking the original paper receipt, giving a mandatory reason and an explicit "Revisé el recibo original" confirmation. The current value lives in a new cash payment row; the change and a `cash_correction` audit fact holding the previous and new values are written in one transaction. Mercado Pago and complimentary confirmations are never touched.

## Decisions

- **Scope (approved 2026-10-21, #104 comment):** any event administrator; amount or receipt number of a confirmed cash payment; reason plus "Revisé el recibo original" confirmation; no attachments; the new receipt must be unique among the event's cash payments; previous values kept in the audit. Out of the MVP: cash on the wrong registration, cash recorded without money, missing or disputed original receipt.
- **Receipt check (2026-10-21):** the approved checkbox replaces the older "type the original receipt and it must match" wording in `docs/product/november-2026-mvp-delivery-slices.md` Slice 5; the docs are aligned in task 4.
- **Storage (2026-10-21):** a new current-state table, one row per cash-confirmed registration (`event_id`, `event_registration_id`, `amount_cents` > 0, `receipt` nullable), unique on `(event_id, receipt)` when the receipt is set. The migration backfills it from the existing `cash_confirmation` audit facts. Cash confirmation writes the row in the same transaction as its audit fact; the correction updates it; registration search reads it. The audit stays the append-only history.
- **Receipt uniqueness (2026-10-21):** the table's unique index replaces the `0029` partial index on the audit table, which is dropped; otherwise a corrected receipt would stay taken by the historical fact. Same case-sensitive comparison and the same `receipt_taken` error as today.
- **Amount (2026-10-21):** any positive amount is accepted, as at confirmation. When it differs from the registration's pass total, the screen warns before confirming but does not block.
- **Legacy rows (2026-10-21):** a confirmation without a receipt (before #125) can get one through a correction, with the same rules; the audit records the null previous receipt.
- **Reason:** mandatory, 1 to 500 characters after trimming, stored in the audit `note`, as in the other corrections.
- **Out of scope:** reference and note edits, moving cash to another registration, unconfirming, Mercado Pago or complimentary confirmations, the correction history view.
